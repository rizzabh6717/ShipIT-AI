# Deterministic vs LLM Re-ranking in ShipIT

ShipIT's AI matching engine ranks candidate drivers with one of two strategies:

1. **Deterministic heuristic** — a fixed, weighted scoring formula.
2. **LLM re-ranking** — a large language model (via LangChain + OpenRouter/OpenAI) that re-ranks the candidate set.

The two modes share the **same retrieval stage** (pgvector semantic search). Only the ranking step differs. This document explains why both modes exist, why the architecture is *retrieval-first, re-rank-second*, and what the trade-offs are.

---

## Why deterministic mode exists

The heuristic ranking is a transparent, fixed formula over five explainable signals:

```
score = 0.35·route_overlap
      + 0.15·pickup_proximity
      + 0.15·deadline_feasibility
      + 0.20·driver_reliability
      + 0.15·vehicle_capacity
```

- **Works fully offline.** No API key, no network, no vendor dependency.
- **Zero API cost.** Embeddings are generated by a deterministic feature-hash embedder; ranking is pure Python.
- **Low latency.** The whole pipeline averages ~14 ms on the evaluation set (retrieval ~14 ms, ranking < 1 ms).
- **Fully reproducible.** Same inputs → same ranking, bit-for-bit. This makes the evaluation framework and CI tests deterministic.
- **Easy to test.** Every component (`app/ai/explainer.py`) is a pure function of (parcel, driver, route).
- **Explainable.** Every score is a weighted sum of interpretable signals, and the API returns human-readable reasons ("Route overlap: 86%", "Pickup detour: 0.0 km", "Driver reliability: 4.9/5").

This is the **production default** for cost-sensitive or air-gapped deployments.

## Why LLM re-ranking exists

The heuristic is good but "flat" — it treats route similarity, distance, and reliability as weighted averages with no notion of context.

- **Better semantic understanding.** An LLM understands that "IGI Airport, New Delhi" is a single destination, that a parcel for "Cyber City" is best served by a Gurgaon-corridor driver, and that an urgent legal-document courier favors speed.
- **Better handling of ambiguous routes.** When two drivers cover the same corridor (near-ties), the LLM can reason about waypoint coverage, direction of travel, and time-of-day realities that a linear formula cannot.
- **Better natural-language reasoning.** The model weighs trade-offs conversationally — e.g. "accept a small pickup detour for a far better rated driver" — instead of applying rigid weights.
- **Better explanations.** LLM reasons are free-form and contextual ("Driver follows the DND flyway which is fastest at this hour"), complementing the structured bullets.

## Why retrieval-first, LLM re-rank-second

The architecture deliberately separates concerns:

```
                retrieval (pgvector)           ranking
drivers ──────►  top-K candidates ──────────►  deterministic OR LLM ──► ranked matches
 (thousands)    (~10, cheap, <20ms)            (small set, LLM-friendly)
```

1. **Cost control.** Running an LLM over *every* driver would be expensive and slow. pgvector shrinks the search space from thousands of drivers to a small candidate set (top-10) in milliseconds, so the LLM call is bounded, cheap, and predictable.
2. **Latency.** Retrieval is a single indexed ANN query (~14 ms). Re-ranking only 5–10 candidates keeps the LLM latency (~100–800 ms) acceptable, whereas ranking 1,000 drivers would be unusable.
3. **Recall safety net.** The HNSW index + cosine similarity is excellent at *recall* (never dropping the right driver), even when its *precision* is imperfect. The LLM then adds precision on top.
4. **Graceful degradation.** If the LLM call fails, times out, or has no API key, the pipeline falls back to the deterministic ranking — the endpoint never breaks.
5. **Testability.** Retrieval and ranking are independently testable; the evaluation framework benchmarks each stage separately (retrieval vs ranking latency).

This is the standard **retrieve-and-rerank** pattern used in production search and RAG systems: a cheap, high-recall first stage followed by an expensive, high-precision second stage.

## Trade-off summary

| Dimension        | Deterministic heuristic            | LLM re-ranking                        |
|------------------|------------------------------------|---------------------------------------|
| Offline          | Yes                                | No (needs API key)                    |
| Cost             | Zero                               | Per-request (small, bounded)          |
| Latency (rank)   | < 1 ms                             | ~100–800 ms                           |
| Reproducibility  | Bit-for-bit                        | Model-dependent, stochastic           |
| Explainability   | Structured bullets (deterministic) | Free-form reasoning                   |
| Ambiguity handling | Weighted, formulaic               | Contextual, semantic                  |

## Recommended deployment strategy

- **Default:** deterministic heuristic (offline, free, low latency, explainable).
- **Escalation:** for high-value / ambiguous parcels (flagged by near-tie scores or high `item_value`), run LLM re-ranking on the top candidates.
- **Production guardrails:** keep `ai_match_top_k` small (10), cache LLM rankings, and always keep the heuristic as the fallback.

## Measuring the difference

The evaluation framework (`backend/evals/evaluate_matching.py`) can run both modes on the same dataset:

```
python backend/evals/evaluate_matching.py --mode deterministic
python backend/evals/evaluate_matching.py --mode llm
python backend/evals/evaluate_matching.py --mode deterministic --compare   # side-by-side table
```

See `backend/evals/results/latest_results.md` for the current metrics and the Deterministic vs LLM comparison table. When no LLM key is configured, `--mode llm` runs the heuristic and the report notes the fallback, keeping the evaluation honest and reproducible.
